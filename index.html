🦫 GitButler 中文版使用指南

本文档基于 GitButler 官方文档 整理，涵盖从入门到进阶的全部核心操作。读完本文，你将学会如何在不切分支的情况下并行开发多个功能。

💡 一句话概括

GitButler 让你在同一工作目录下同时编辑多个分支，所有 commit 自动归属到指定虚拟分支，无需手动 checkout 切换。

为什么要用 GitButler？

传统 Git 的问题是：你只能同时在一个分支上工作。想切换任务时，必须先 stash 当前改动、checkout 到另一个分支，然后再 pop 回来。这个过程容易出错、丢数据。

GitButler 重新设计了这段流程——它是写代码和推送代码之间的桥梁，专注于你本地的工作目录：

  • 并行分支：同时应用多个分支，各自独立 commit
  • 拖拽式 commit 编辑：drag & drop 合并、拆分、重排 commit
  • 自动冲突处理：rebase 时遇到冲突继续推进，稍后逐个解决
  • 操作历史：随时回退到任意时间点
  • AI 辅助：自动生成 commit message 和分支名

核心概念

1. Target Branch（目标分支）

GitButler 需要一个"主线"作为基准。通常是你团队的 main 或 master 分支。所有虚拟分支都以它为基础创建。

2. Workspace（工作区）

GitButler 的核心视图。你的所有未提交改动都在这里，同时可以挂载多个并行分支。你不需要手动切换分支，所有改动自动归属到对应的分支车道（lane）。

⚠️ 重要：Workspace 分支机制

GitButler 会创建一个特殊的 gitbutler/workspace 分支来合并所有已应用的分支。你在终端执行 git status 时看到的就是这个合并后的状态。

不要在 GitButler 模式下直接用 git commit 提交——这会绕过 GitButler 的追踪系统，导致 UI 不更新。正确做法是：在 GitButler 界面中点击 "Commit" 按钮，或在对应 lane 里操作。

3. Virtual Branch（虚拟分支）

虚拟分支是 GitButler 的核心创新。它们不是真正的 git 分支，而是 GitButler 自己管理的逻辑分支：

  • 可以同时 Apply（应用）多个虚拟分支到你的工作目录
  • 每个分支有自己独立的暂存区
  • 可以独立 commit、push
  • 可以随时 Unapply（卸载）来暂时收起

4. Branch Stack（分支栈）

当一个功能的实现需要多个相关分支（比如先改数据结构，再改 UI），可以把它们组成一个 stack，从底到顶依次依赖。

Workspace 工作区

Workspace 是 GitButler 的主界面。左侧是分支列表，中间是当前分支的 commit 历史，右侧是文件改动预览。

基本布局

区域说明
左侧分支栏已应用的虚拟分支、未应用的分支、远程分支
中间 Lane每个虚拟分支显示为一个"车道"，里面有 commit 列表
右侧预览选中文件或 commit 时显示 diff
底部状态栏显示 uncommitted changes（未提交的改动）

Apply / Unapply

  • Apply：把一个分支的改动放到工作目录中（同时应用多个）
  • Unapply：从工作目录移除该分支的改动，但保留分支和 commit

虚拟分支详解

虚拟分支是 GitButler 区别于普通 Git 客户端的最大特色。

工作原理

与普通 Git 每次只能在一个分支上不同，GitButler 把所有并行分支的改动叠加到你的工作目录。每个分支有一列（lane），每个 lane 有自己的暂存区和 commit 历史。

关键特性

  • 拖拽分配：把一个文件的改动从一个 lane 拖到另一个 lane
  • 独立暂存：每个 lane 有自己的 staging area
  • 自动 clean：分支合并到上游后，GitButler 自动清理该虚拟分支
  • WIP 支持：分支可以有未提交的 WIP 状态（自动保存为 WIP commit）

创建分支与提交

第一步：导入项目

  1. 打开 GitButler Desktop
  2. 点击 "Add local project" 选择你的仓库目录
  3. 选择 Target Branch（通常是 origin/main 或 origin/master）
  4. 可选：登录 GitButler 账号以启用 AI 功能
  5. 可选：连接 GitHub/GitLab 以支持 PR/MR

第二步：创建虚拟分支并编辑文件

  1. 在工作目录中编辑文件（GitButler 会自动检测到改动）
  2. 在 "Unassigned changes" 区域可以看到所有未归属的改动
  3. 点击 "Create Branch" 或直接拖拽文件到新建的 lane 中
  4. 为分支命名（比如 feat/遥控语音播报）

第三步：Commit

  1. 在目标 lane 中点击 "Start a Commit"
  2. 填写 commit message（或用 "Generate Message" 让 AI 自动生成）
  3. 点击 commit 完成
✅ 正确流程总结

改文件 → GitButler 自动检测 → 拖到对应 lane → 点击 Commit → 推送。全程不需要 git checkout 或 git stash。

编辑 Commit（拖拽式操作）

GitButler 把复杂的 rebase 操作变成了可视化拖拽：

Squash（合并 commit）

把一个 commit 拖到另一个 commit 上方 → 自动 squash。

Split（拆分 commit）

  1. 在两个 commit 之间插入一个 empty commit（点击 commit 旁的 + 按钮）
  2. 把要拆出来的文件从原 commit 拖到新 empty commit 上
  3. 编辑新 commit 的 message

Reorder（重排顺序）

直接拖拽 commit 到新的位置，GitButler 自动 rebase 所有后续 commit。

Undo（撤销 commit）

展开 commit，点击 "Undo" → 该 commit 的改动变为未提交状态（不会丢失）。

Uncommit 单个文件

展开 commit → 点击某个文件 → 点击 "Uncommit" → 仅该文件回到未提交状态。

Edit Mode（编辑模式）

点击 commit 上的 "Edit commit" 按钮，GitButler 会暂存其他改动，checkout 出该 commit 让你直接编辑工作目录，完成后点击 "Save and exit" 自动 amend 并 rebase 上方 commit。

Absorb（吸收改动到已有 commit）

修改文件后，把文件直接拖到目标 commit 上 → 自动 absorb 并重 base。

冲突处理

GitButler 的冲突处理方式是：不停止 rebase，遇到冲突的 commit 标记为 Conflicted，继续处理后续的，等你有空再逐个解决。

操作流程

  1. 点击 "Update" 同步上游 → GitButler 告诉你哪些分支有冲突
  2. 展开冲突的 commit → 点击 "Resolve Conflict"
  3. 进入 Edit Mode，此时其他分支被暂时移除，只留下这个 commit 的冲突状态
  4. 像普通编辑一样修改文件解决冲突
  5. 点击 "Save and Exit" → GitButler 自动提交修复并重 base 后续 commit
  6. 如果不想解决，点击 "Cancel" 返回正常状态

同步上游（Pull / Rebase）

常规更新

当主分支有新 commit 时，GitButler 会提示 "Update" 按钮：

  • 点击 Update → 自动 rebase 所有已应用的分支到最新基线
  • 已合并的分支会被自动清理

有人同时推送了同一分支

当别人推了你的分支时，GitButler 会显示远程的新 commit（不需要 merge）：

  • Rebase upstream changes：等价于 git pull --rebase，把你的 commit 移到对方 commit 上方
  • Interactive integration：交互模式，可以重排、跳过、squash 远程 commit

推送与创建 PR

Push

在 lane 上点击 "Push" 按钮即可推送该分支到远程。

Create Pull Request

连接 GitHub/GitLab 后，点击 "Create PR" 或 "Submit for Review" 即可在 GUI 内创建 PR，无需打开浏览器。

Land（直接合并到目标分支）

如果你不需要 Code Review，可以在项目设置中开启 "Land branches directly"，Push 按钮会变成 "Land"，直接快进合并到目标分支。

🚨 Land 的注意事项

Land 会绕过 Code Review、CI 检查和分支保护规则。受保护的分支会拒绝直接推送。

堆叠分支（Stacked PRs）

当一个功能需要多个相关改动，但每个改动需要独立 review 时，使用 Stack：

  1. 在底部分支（基础分支）上 commit 第一个改动
  2. 在该 lane 上点击 "Create new branch" 的堆叠图标
  3. 命名新分支，继续 commit 第二个改动
  4. 重复直到完成所有依赖分支

推送时，GitButler 会自动设置每个 PR 的 base branch 为下方最近的有 PR 的分支。

移动分支间关系

  • 拖拽：把分支 header 拖到另一个 stack 的合适位置
  • Tear off：把分支拖出 stack 区域，变成独立分支

约束：分支不能有冲突、必须至少有一个 commit、不能移动到同一 stack 内。

操作历史与撤销

GitButler 在执行每个重要操作前都会创建一个快照。你可以通过 Operations History（操作历史）面板回退到任意时刻。

使用方式

  1. 点击左侧边栏的 "History" 图标
  2. 找到你想回退的操作
  3. 点击 "Revert" 按钮

支持撤销的操作包括：commit、squash、reorder、update upstream、apply/unapply 分支等。

💡 文件快照

即使没有 commit，GitButler 也会定期快照最近修改过的文件内容。如果误删了文件，可以在 History 中恢复。

恢复丢失的数据

GitButler 极其注重数据安全，即使崩溃也不会丢数据：

虚拟分支的 git 引用

每个虚拟分支都会作为 git ref 保存在 refs/gitbutler/ 下（不在 refs/heads/ 里），你可以直接看到：

git branch -a | grep gitbutler

从 git log 恢复

git log --all --oneline | grep gitbutler

这些引用指向的 commit 包含了该分支的所有文件改动（包括 WIP 状态）。

从 Operations Log 恢复

# 查看 GitButler 的内部操作记录
cat .git/gitbutler/operations-log.toml

里面保存了每次操作前的完整项目快照。

极端情况下的手动恢复

如果 GitButler 完全无法启动且需要手动恢复冲突 commit，参考官方文档的 Fixing Conflicts Outside GitButler 指南，涉及 .auto-resolution、.conflict-base-0 等内部 git 对象的操作。

GitHub 集成

连接步骤

  1. 点击左侧头像 → Settings → Integrations
  2. 选择 Add account → GitHub
  3. 推荐选择 Device Flow（自动生成授权码，在浏览器中完成授权）
  4. 也可以手动粘贴 Personal Access Token（需要 repo + workflow 权限）

创建 PR

连接后，每个 lane 底部会出现 "Create PR" 按钮。点击下方（最靠近 target branch 的）分支开始创建，GitButler 会自动向上设置每个 PR 的 base。

原生堆叠 PR（Stacked PRs）

在 Project Settings → Native GitHub stacked pull requests 中设置：

  • Auto：仓库支持时使用原生堆叠，否则用描述信息（默认）
  • Native：强制使用原生堆叠，不支持则报错
  • Disabled：始终使用描述信息

GitLab 集成

前置条件

  • GitLab Personal Access Token：需要 api scope
  • Project ID：在 GitLab 仓库页右上角三点菜单 → Copy project ID

配置步骤

  1. GitButler → Project Settings → 底部 GitLab 配置区域
  2. 填入 Token 和 Project ID（Token 安全存储在系统 Keychain 中）
  3. 如果是自托管 GitLab，填入 Instance URL
⚠️ 自托管 GitLab 注意

使用自定义 GitLab 实例时，可能需要在 GitButler 中添加自定义 CSP（内容安全策略）以允许连接到你的实例。详见官方 Custom CSP 文档。

常见问题

Q1：我在 GitButler 里 commit 了，但 UI 没更新？

你可能用了 git commit 直接提交，跳过了 GitButler 的追踪。解决方法：

# 1. 确认提交已在目标分支上
git log --oneline <branch-name> -3

# 2. 同步 GitButler 数据库（TOML + SQLite）
sed -i '' 's/<旧commit>/<新commit>/' .git/gitbutler/virtual_branches.toml
sqlite3 .git/gitbutler/but.sqlite \
  "UPDATE vb_stack_heads SET head_sha='<新commit>' WHERE name='<分支名>';"

# 3. 触发刷新
echo $(pgrep -f gitbutler-tauri) > .git/gitbutler/REFRESH

根本解法：永远在 GitButler GUI 中点击 Commit 按钮，不要用 git commit。

Q2：Workspace 分支是什么？为什么 git log 里看到奇怪的 merge commit？

gitbutler/workspace 是 GitButler 用来合并所有已应用分支状态的虚拟分支。当你同时 Apply 多个分支时，GitButler 会把它们的改动合并到这个分支，让 git status 输出看起来正常。这是预期行为，不要手动操作这个分支。

Q3：GitButler 卡住了 / 无法响应？

可能的原因和解决方法：

  • SQLite 数据库锁：检查是否有多個 GitButler 进程在运行 ps aux | grep gitbutler
  • 冲突未解决：进入 Edit Mode 解决冲突后再继续
  • 完全卡死：参考 官方修复指南 进行手动恢复

Q4：如何在没有 GUI 的服务器上工作？

使用 but tui 命令： 

but setup          # 初始化
but branch create <name>   # 创建分支
but apply <name>           # 应用分支
# ... 编辑文件 ...
but commit         # 提交
but push <name>  # 推送

黄金法则（最重要）

🚫 绝对不要做

不要用 git commit 提交代码。GitButler 安装了 pre-commit hook 来阻止你，但如果绕过则会导致数据库不同步。

不要用 git checkout 切换分支。这会让 GitButler 进入混乱状态。

✅ 推荐做法

所有操作通过 GitButler GUI 或 but CLI 完成。

可以用 git log、git diff、git status 查看状态，这些是安全的只读操作。

退出 GitButler 管理模式：but teardown，恢复后就可以正常用 git 了。

Butler Flow 工作流

GitButler 推荐一种轻量级分支工作流（改进版 GitHub Flow）：

  1. 所有工作基于 Target Branch（通常是 main）
  2. 每个改动立即创建分支，即使是小改动
  3. 尽早分享：分支创建后即可 Push，让同事 review
  4. 本地集成测试：可以同时 Apply 多个接近合并的分支进行联调
  5. 独立 review：每个分支单独 review 和合并
  6. 自动清理：合并后虚拟分支自动消失，不产生垃圾
